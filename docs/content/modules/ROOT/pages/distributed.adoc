= Object-Storage Persistence
:navtitle: Object-Storage Persistence

The embedded engine can persist a single `VectorCollection` to an S3-compatible object store that
you control. The collection still runs in-process inside one JVM; object storage provides a durable
copy that a fresh process can use to hydrate its local cache.

This mode is useful when local disk is ephemeral or when collection data must survive application
replacement. It is not a multi-node database: one application process owns the active collection,
and there is no distributed query coordinator or cross-node cache.

== Add the S3 runtime

The base `vectors` dependency deliberately does not pull in the AWS SDK. Add the opt-in
`vectors-storage-s3` artifact when the application uses `S3StorageBackend`:

[tabs]
====
Gradle::
+
[source,kotlin,subs="attributes+"]
----
dependencies {
    implementation("com.integrallis:vectors:{vectors-version}")
    implementation("com.integrallis:vectors-storage-s3:{vectors-version}")
}
----

Maven::
+
[source,xml,subs="attributes+"]
----
<dependencies>
    <dependency>
        <groupId>com.integrallis</groupId>
        <artifactId>vectors</artifactId>
        <version>{vectors-version}</version>
    </dependency>
    <dependency>
        <groupId>com.integrallis</groupId>
        <artifactId>vectors-storage-s3</artifactId>
        <version>{vectors-version}</version>
    </dependency>
</dependencies>
----
====

== Configure a backend

`S3StorageBackend` supports AWS S3 and compatible endpoints such as Cloudflare R2, Google Cloud
Storage, and MinIO. Endpoint overrides, path-style addressing, and static credentials make the same
API usable in local and hosted environments.

[source,java]
----
StorageBackend objectStore = S3StorageBackend.create(
    URI.create("http://localhost:9000"), // omit the override for AWS S3
    "vectors",                           // bucket
    "us-east-1",                         // region
    "minioadmin",                        // access key
    "minioadmin");                       // secret key
----

Use environment-backed or workload-identity credentials in production instead of embedding
credentials in application source.

== Persist a collection

Pass the backend and an object-key prefix to the collection builder. `commit()` writes an atomic,
generation-based durable snapshot after updating the local collection:

[source,java]
----
try (VectorCollection collection = VectorCollection.builder()
    .dimension(4)
    .metric(SimilarityFunction.COSINE)
    .indexType(IndexType.HNSW)
    .storagePath(Path.of("/var/lib/myapp/cache/demo"))
    .objectStore(objectStore, "demo/")
    .build()) {

  collection.add(Document.of("a", new float[] {1, 0, 0, 0}, "alpha"));
  collection.commit();
}
----

When `build()` opens the same prefix later, the collection hydrates its local cache from the
committed object-store generation. Queries continue to run locally in the JVM after hydration.

== Operational boundaries

* Use one active application process per collection prefix.
* Treat the local `storagePath` as a cache and the object-store generation as the durable copy.
* Give each independent collection a distinct object-key prefix.
* Keep bucket credentials outside source control and grant only the required object permissions.
* Account for object-store latency during startup hydration and commits.
