= Semantic Caching
:navtitle: Semantic Caching

Vectors ships a small caching layer built for AI workloads: an exact-match cache for embeddings, and
a **semantic cache** that answers a query from a *near-duplicate* earlier query instead of only an
identical one. The common payoff is skipping an expensive embedding or LLM call when a semantically
equivalent request has already been served.

There are two interfaces:

* `VectorCache<K, V>` — an exact-key cache with a Caffeine default and a JSR-107 (JCache) backend.
* `SemanticCache<V>` — a similarity cache: `lookup(queryEmbedding)` returns a hit when a stored
  entry is within a cosine threshold, so paraphrases hit the same cached answer.

== Exact-match cache

`CaffeineVectorCache` is the default `VectorCache` — a bounded, optionally expiring cache with hit,
miss, and eviction stats. `getOrCompute` is the single-flight hot path: on a miss it invokes the
loader once, even under concurrency.

[source,java]
----
try (VectorCache<String, float[]> cache =
    CaffeineVectorCache.<String, float[]>builder()
        .maximumSize(10_000)
        .expireAfterWrite(Duration.ofMinutes(5))
        .build()) {

  float[] embedding = cache.getOrCompute("hello world", text -> embeddingModel.embed(text));

  CacheStats stats = cache.stats();   // hits, misses, evictions, hitRate()
}
----

== Semantic (similarity) cache

`VectorDbSemanticCache` implements `SemanticCache<V>` over a `VectorCollection`. `put` stores an
embedding and a serialized payload; `lookup` runs a top-1 search and returns a hit only when the
score clears the configured threshold (default cosine `0.92`). This is the LLM-response cache: a
paraphrased prompt whose embedding is close enough to a cached one returns the stored answer.

[source,java]
----
VectorCollection collection = VectorCollection.builder()
    .dimension(embeddingModel.dimensions())
    .metric(SimilarityFunction.COSINE)
    .indexType(IndexType.FLAT)
    .build();

try (SemanticCache<String> cache =
    VectorDbSemanticCache.builder(collection, PayloadCodec.identity())
        .threshold(0.92)                 // cosine; higher is stricter
        .closeCollectionOnClose(true)
        .build()) {

  // Cache an answer keyed by its prompt embedding
  cache.put("q1", embeddingModel.embed("How do I reset my password?"), "Go to Settings → Security…");

  // A paraphrase hits the same entry when within threshold
  Optional<SemanticCache.Hit<String>> hit =
      cache.lookup(embeddingModel.embed("password reset steps?"));
  hit.ifPresent(h -> System.out.println(h.value() + " (score " + h.score() + ")"));
}
----

`PayloadCodec<V>` serializes the cached value; `PayloadCodec.identity()` handles `String` payloads,
and you supply an encode/decode pair for richer types. Use `thresholdRaw(threshold, higherIsBetter)`
for Euclidean metrics (where lower is better), and `admissionPolicy(...)` to gate which values are
allowed into the cache.

== JCache (JSR-107) backend

`JCacheVectorCache` wraps any JSR-107 `Cache`, so an existing Ehcache / Hazelcast / Infinispan
deployment can back the exact-match cache. Stats report hits and misses; eviction count and size are
left to the underlying provider.

[source,java]
----
Cache<String, float[]> backing = cacheManager.createCache("embeddings",
    new MutableConfiguration<String, float[]>().setTypes(String.class, float[].class));

VectorCache<String, float[]> cache = new JCacheVectorCache<>(backing);
cache.put("hello", embeddingModel.embed("hello"));
----

== Framework decorators

For Spring AI and LangChain4j the cache is applied as a drop-in decorator around the model or store
— no call-site changes. Each framework offers both kinds, and the distinction matters:

[cols="2,1,3", options="header"]
|===
| Decorator | Matching | Use when

| `CachingEmbeddingModel`, `CachingChatModel`
| Exact key
| The same prompt recurs verbatim. Cheapest lookup, no embedding call on the read path.

| `SemanticCachingChatModel`
| Similarity
| Users phrase the same question differently. "How do I reset my password" is served from
  "I forgot my password".
|===

`SemanticCachingChatModel` embeds the request and serves a hit when an earlier request is within the
cache's threshold. Two responses are deliberately never served from it:

* **Tool calls.** A response asking the caller to run a tool is an instruction, not an answer.
  Replaying it would skip the tool and hand back a stale result, so those responses are returned but
  never stored.
* **Output generated under different request options.** An embedding captures only the text, so a
  hit could otherwise return output produced at a different temperature or token limit. Each entry
  records its options as an attribute and every lookup filters on them.

[source,java]
----
ChatModel cached = new SemanticCachingChatModel(delegate, embeddingModel, semanticCache);
----

Cache hits retain the model name from the original response and expose both the
hit and its similarity through response metadata. Prefer the typed helpers when
updating usage or cost displays:

[source,java]
----
ChatResponse response = cached.call(prompt);
if (SemanticCachingChatModel.isCacheHit(response)) {
  double similarity = SemanticCachingChatModel.cacheSimilarity(response).orElseThrow();
}
----

For a composed RAG prompt, mark the message metadata with the text that represents
the user's semantic intent. This prevents shared instructions and retrieved context
from making unrelated questions look similar:

[source,java]
----
var message = UserMessage.builder()
    .text(completeRagPrompt)
    .metadata(Map.of(SemanticCachingChatModel.CACHE_KEY_METADATA, contextualUserQuery))
    .build();
ChatResponse response = cached.call(new Prompt(message));
----

Without this metadata, the complete prompt remains the key for backwards
compatibility.

The decorators require a cache that stores attributes and reject one that does not at construction,
so the mismatch surfaces when you wire the application rather than mid-conversation.

Integration details: xref:spring-ai.adoc[Spring AI] and xref:langchain4j.adoc[LangChain4j].

== Scoping a lookup with attributes

Similarity alone does not decide whether a cached answer may be served. A completion generated at
temperature 0.9, for another tenant, or by another model can be an excellent semantic match and
still be the wrong thing to return. Entries carry attributes describing the conditions they were
produced under, and a `CacheFilter` names the conditions the caller accepts.

[source,java]
----
cache.put("reset password", embedding, answer,
    Map.of("tenant", "acme", "model", "gpt-5"));

Optional<SemanticCache.Hit<String>> hit = cache.lookup(embedding,
    CacheFilter.matching("tenant", "acme").and(CacheFilter.matching("model", "gpt-5")));
----

A filter constrains only the attributes it names; anything else on the entry is free to vary.
`CacheFilter.all(Map)` matches a whole map at once, and `CacheFilter.any()` accepts everything.

Filtering runs inside the search rather than over the single nearest result. The nearest entry
overall is frequently not the nearest entry the caller may use — a verbatim repeat of the prompt at
the wrong temperature sits closer than a paraphrase at the right one — so testing a top-1 result
after the fact reports a miss where a usable entry exists. `lookupTopK` exposes the same ranking
directly.

`supportsAttributes()` reports whether an implementation stores them. `VectorDbSemanticCache` does;
an implementation that does not rejects a non-empty attribute map from `put` rather than dropping
it, because a filtered lookup over entries with missing attributes serves exactly the answers the
filter was added to prevent.
